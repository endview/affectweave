## 1. 先明确归属与实际原因

**回复表达主要修改 AffectWeave 仓库。** 是否分段、怎样提示模型、人物模式、分段位置与均衡合并均由扩展决定。FreeAgent 继续只接收无损 `reply_parts`，不读取人物参数决定怎么说话。

| 责任 | 仓库及落点 | 本次范围 |
| --- | --- | --- |
| 表达策略与默认值 | AffectWeave：`internal/extension/`、`internal/affect/reply.go`、`extension.json`、接入文档 | 空行分条提示、共同的模式解析、结构保护、均衡合并、无损切片；是本项主交付 |
| 能力选择与设置呈现 | FreeAgent：已有会话能力选择、通用扩展字段、扩展详情页 | 来源反馈与保存回归；只修证实的通用选择问题，不硬编码“默认选 AffectWeave” |
| 平台发送 | FreeAgent 的 TG 渠道、现有 outbox | 每段独立发送、首条引用、格式与回执；不增加表达模式或分段算法 |
| 未决交付 | FreeAgent dev.7 未决清单 | 引用原 outbox 项并复用续送/放弃，不另建扩展投递数据库 |

扩展设置页面目前由 FreeAgent 前端自身代码呈现；这不改变字段语义和策略属于 AffectWeave 的边界。卸载扩展后其表达入口消失，普通 Core 不获得任何分段偏好。

`expression_enabled=false` 不阻止自然段拆分；拆分发生在表达建议开关检查之前。不需要为本功能开启自动分析、贴纸、反应或主动对话。

## 2. 首先核对选择；现版本即可使用的步骤

### 2.1 能力选择的来源

已核实的公共规则如下，不新增选择层级：

1. 请求明确携带能力集合时，以该集合冻结本轮，空集合也表示明确选择。
2. 否则读取 `chat/capabilities/<conversation>`，已有记录即沿用其内容，并剔除已停用的能力。
3. 没有会话记录时，本地/Owner 私聊使用全局已启用能力；非 Owner 公开空间默认空集合。
4. `/new` 创建独立会话，不复制旧会话的能力及人物覆盖；新会话按上述默认规则解析。`/switch` 读取目标会话自己的选择；跨空间移动沿用现有权限隔离，不偷带原空间选择。

第一步核对同一会话的已保存选择、最近变更、普通 Run 冻结值和实际扩展上下文。回归刷新、快速切页、快照未到达、能力目录刷新、保存冲突及停用/再启用：不能把“尚未加载”自动提交成“用户取消全部”，也不能把用户明确取消自动恢复。修复仅针对证实的路径；没有新增一套能力继承系统。

### 2.2 不等待发版的使用路径

1. 在 Web 打开对应的 **TG 会话**，在能力弹层选中 AffectWeave 并选回所需人物，核对保存结果；保留原有 Skill/MCP 选择。
2. 在“设置 → 能力 → 扩展 → AffectWeave → 扩展默认设置”将扩展默认回复方式设为“自然分段”，点击“保存扩展配置”，刷新回读。最大段数沿用默认 3 即可。
3. 该默认对选中扩展且未覆盖方式的后续请求有效；Web 的“本次请求设置”只作用于下一次页面提交，不会自动变成 TG 长期默认。不要在这一步重写已经冻结的 Run 或 outbox。
4. 原 TG 会话可接收新请求后，明确要求真实模型“请分成两条简短回复，两条之间用一个空行分隔，每条一到三句，不加编号”。现有算法已能分开发出这种结构；模型未给空行时仍是一条。

若当前 Run 仍被 UNKNOWN 阻塞，先按关联主方案协调该问题，不靠强制结束、重放或 `/new` 绕过未决事实。本节是可操作路径，本次文档审阅没有替用户改线上配置或发送消息。

## 3. AffectWeave 1.6.0-dev.3：表达规则

### 3.1 在已有上下文中给出分条偏好

只有扩展被选中、当前有可用回复渠道、有效模式为 `paragraphs` 且有效上限大于 1 时，附加一段有界表达偏好。例如：

> 如需分条表达，用空行分隔，最多 K 条，每条通常一到三句。单换行只作条内排版。不要为凑条数拆句；代码、表格、列表和公式保持完整。遵守用户本次明确的格式要求。

这段内容属于已选择扩展的低优先级表达偏好，不覆盖 Core 规则、权限或用户明确要求，不把历史引用提升为指令。不增加模型调用，不在 Core 系统提示中硬编码。

使用现有 `context.prepare` 扩展块及 `tail` 位置；将提示与原人物块一起计入扩展上下文预算。预留不超过 512 UTF-8 字节，预算不足时省去该提示，不能挤掉人物身份/边界或绕过 Core 总预算。未选人物但显式启用自然分段时，可返回只含表达偏好的小块，不虚构人物。`single` 不注入分条提示。

### 3.2 模式在生成与交付时一致

`context.prepare` 和 `turn.finished` 共用扩展内的同一个纯函数，输入为本轮冻结设置、对应已采纳输入的冻结人物状态与渠道上限：

| 模式 | 规则 |
| --- | --- |
| 未设置 / `single` | 一条逻辑回复 |
| `paragraphs` | 在安全空行边界拆分 |
| `character` | 沿用现有直接度 < 0.7 且表达参数 ≥ 0.4 的规则；满足则按自然分段，否则一条。无人物时一条 |
| 任意模式但有效上限为 1 | 一条逻辑回复，不注入多条提示 |

有效上限是扩展已保存上限（未设置为 3）与 Host 提供上限的较小值。人物参数采用冻结状态，不临时回读新人物或新增随机决策；运行中采纳新输入遵循现有安全边界，最终切分使用与生成所用提示一致的状态。自动分析与表达建议开关不作为显式自然分段的前置条件。

### 3.3 只按安全空行切分，超限时均衡合并

- **不做单换行切分，也不加入“短句长度”猜测。** 模型决定表达边界，扩展验证该空行能否安全拆开。提示不是格式保证，没有安全边界时保留一条。
- 完整围栏/缩进代码、公式、列表、表格、引用及跨段 Markdown 关联不得从内部拆开。标题与所属内容保持一起；无法证明引用式链接等跨段结构独立时合并相关块或保留一条。现算法只保护部分代码/公式，结构保护需要在扩展补齐。
- 安全段数不超过上限时直接采用。超过上限时合并相邻段，不再采用固定“前两段各一条、剩余全部最后一条”。按剩余源码 rune 数除以剩余条数确定目标，取最接近目标且给后续每条至少留一个完整段的安全边界；并列取较早边界。六个等长段、上限三条应得到约 2+2+2。不得为了均衡拆代码块、改字或重排。
- “自然分段”是有边界时多条发送，一段短回答仍可为一条。平台因长度限制产生的必要分片不是扩展选择的新表达模式。

### 3.4 原文与发送文本分开校验

原文切片将**分隔空行及其换行符全部归前一段**，下一段从其正文起点开始；开头空白属于第一段、末尾空白属于最后一段，CRLF 原样保留。全空白内容不生成片段。始终要求 `strings.Join(reply_parts, "") == 原回答`，不能先 TrimSpace 再校验。

平台文本是经过 Markdown 渲染的另一份表示。沿用 TG 渲染器现有尾部换行处理；确需清理装饰空行时，在渠道渲染阶段完成并校准 entities，然后冻结最终请求。不能在派发前随意裁剪冻结文本，也不能全量 TrimSpace 破坏缩进代码、硬换行或 UTF-16 偏移。渲染后空文本不能变成一次空发送，应按现有准备失败/原文回退规则处理并留证。

## 4. FreeAgent 通用交互补项：不恢复工具栏控件

上一轮移走的是**输入器工具栏**中的回复方式，现有能力弹层入口继续保留。本项不再增加工具栏标签、下拉框或固定提示条。

- 扩展默认字段在扩展详情的常用设置区域呈现，复用原保存表单和字段值；高级 JSON 同步同一草稿，不出现第二个值。AffectWeave 的字段声明与文案由扩展提供。
- 在已有下拉项中补充实际继承值及来源。例如“继承：完整一条（扩展默认）”。只扩充通用扩展元数据；声明未知时显示“由扩展决定”。`character` 显示“按人物表达”，前端不计算人物阈值或承诺本轮一定几条。
- 保留下一次页面提交的覆盖语义与全局默认的差别；扩展未选中时，在已有能力区域说明不生效。
- 草稿、保存按钮、错误、冲突、刷新回读和人物/表达设置交替保存属于**已有框架的回归验收**；有失败才修对应缺陷，不重写设置框架。

CLI/AI 继续复用通用扩展设置与现有确认，保存后读回实际值；不能在未选扩展的 Run 内强行越权改人物状态。首次恢复会话选择可通过当前可用的 Web/CLI 完成。

## 5. Telegram 与未决投递：沿用公共机制

沿用 `turn.finished → reply_parts → freezeReplyText → outbox → Telegram`。最终答案只交付一次；不增加“先流式发整条、再补发分段”。typing、进度/审批通知与答案正文分开计数；Web/GUI 仍是一份完整流式回答。

群聊沿用现有空间授权、提及/回复触发和能力选择规则：非 Owner 公开空间不自动继承私聊能力；明确选中扩展后按已保存方式执行。全局默认仍为 `single`；用户改成自然分段会影响所有选中且未覆盖的会话，保存时说明范围。不新增群聊分段开关，不为分段放开公开空间的人物可见性。

TG 的整组回答只在**第一个实际文字消息**上引用原用户消息，后续逻辑段及平台长度分片不重复附 reply-to；目标会话与主题路由保持原绑定。两种现有派发路径都需修正，不能只改直接发送而漏掉远程 outbox。已冻结旧组不回写或重发。

状态展示沿用现有逐条状态，投递记录分别显示逻辑段数、平台消息总数和已确认发送数。片段间隔沿用已保存设置；零间隔也必须是独立消息。

中间一段 UNKNOWN 时，既有 outbox 暂停未派发尾段。dev.7 清单引用该 operation，显示“已确认发出 X 条，第 Y 条未确认，后续 Z 条暂未发送”，绑定现有组与摘要；不复制为新的 Attempt。Web/CLI 在回执变化后可见，TG 在用户下一次查询状态/投递记录时给出同一说明，不因原发送未知再自动外发一条告警。

**续送由用户在现有入口明确确认。** 沿用“仅续送未派发部分”/CLI 等价操作，渠道下次正常轮询后恢复顺序发送；未知段不重发，原未知事实保留。“已审阅不确定性”不等于“已送达”，模型不能用一句成功判断自行放行。用户也可放弃尾段；迟到回执只更新原项，不触发自动续送。旧 Core 已有此管理入口，新清单仅汇总并链接它。

| 真人 TG | 生产只保留现有单一 Bot 消费进程。通过真实 DeepSeek 明确要求两条简短回复且用空行隔开，记录模型实际输出、逻辑段数与真实消息 ID/回执；客户端核对独立消息，Web 保持一份回答 |

固定文本只用于模拟 Provider/TG，不要求真实模型逐字输出固定文案。真实模型未遵循分条要求时如实记录不达预期，不能重复发送正文凑条数；没有安全边界仍为一条是算法行为，不算模拟两段验收通过。独立验证实例不能拿生产 Bot token 同时轮询；真人检查使用已明确授权的会话与请求，未获授权则记 NOT_RUN。
